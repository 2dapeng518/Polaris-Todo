# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Polaris is a local-first Windows 11 to-do app: Electron 45 main process, sandboxed React 19 renderer, better-sqlite3 storage, NSIS packaging. The interface is bilingual — Simplified Chinese (default) and English; all user-facing copy goes through the hand-rolled i18n dictionaries in `src/shared/i18n/` (see Interface language below), never a hardcoded single-language string. Code comments stay Chinese.

Visual decisions follow `design-system/polaris-design/SKILL.md`: one four-point star, one teal signal, night is cool ink and day is warm porcelain, Manrope/Inter/Noto Sans SC/Geist Mono.

## Commands

```bash
npm install
npm run dev         # electron-vite dev server
npm run typecheck   # tsc for node + web tsconfigs
npm run build       # electron-vite build -> out/ (production: harness stripped at build time)
npm run smoke       # auto-rebuilds with POLARIS_HARNESS=1, then launches Electron with POLARIS_SMOKE
npm run verify:themes # WCAG contrast + theme registry invariants
npm run verify:datetime # date/time pure-function invariants (plain Node, no Electron)
npm run verify:pure # quick-add parse + retention + recurrence + CSV truth tables (plain Node, no Electron)
npm run preview     # preview the production build
npm run build:win   # build + electron-builder NSIS --publish never -> dist/
npm run build:mac   # build + electron-builder --mac --publish never
npm run release:win # build + NSIS --publish always (needs GH_TOKEN; uploads to GitHub Releases)
npm run make:icon   # regenerate build/icon.png / .ico / .icns
```

- There is no ESLint, Prettier, or vitest/jest-style unit-test framework — but there is a pure-function verification layer: `verify-datetime.mjs` and `verify-pure.mjs` import the TS modules straight into Node (type stripping) with an injected clock. The automated checks are `npm run smoke`, `npm run verify:themes`, `npm run verify:datetime` and `npm run verify:pure`; all exit non-zero on failure, and the three verify scripts run in CI (`.github/workflows/ci.yml`) while smoke stays local (Windows + Electron). Run `npm run smoke` after behavior changes (it rebuilds with the harness itself — never runs stale `out/`), `npm run verify:themes` after theme changes, `npm run verify:datetime` after touching `lib/dateTime.ts`, and `npm run verify:pure` after touching `shared/quickAddParse.ts` / `shared/retention.ts` / `shared/recurrence.ts` / `shared/csvExport.ts` / `shared/backupNames.ts` / `shared/mirror.ts`. The datetime script injects the clock — the only way to cover wall-clock boundaries deterministically, since hitting 23:59 by running the real UI is a 60/86400 chance. `verify:pure` re-runs the harness's truth tables in seconds without Electron (293 assertions): its tables are a verbatim port of `runParseAssertions()`/`runRetentionAssertions()`/`runRecurrenceAssertions()`/`runCustomRecurrenceAssertions()`/`runBackupNameAssertions()`/`runMirrorAssertions()` plus the CSV export table (mirrored by the smoke `csvExportWorks` guard; CSV import was removed 2026-11-19) and **both copies must be updated together** (the harness originals stay — E2E still runs them). Both scripts register `scripts/ts-resolve-hooks.mjs` before dynamically importing the TS modules: plain Node understands neither the `@shared/*` alias nor extensionless/directory imports, so the hook maps them to real `.ts`/`index.ts` files; it also redirects `rrule` to its `dist/esm` build (the CJS `main` bundle's named exports are invisible to Node) and forces `format: 'module'` on those files — same code the bundler picks via the `module` field. `verify-pure.mjs` pins `TZ=Asia/Shanghai` because the `formatParsedDue` expectations are UTC+8 wall-clock literals.
- `npm run smoke` drives the real UI through `webContents.executeJavaScript` against a temporary userData profile, so it does not touch a running app's database: quick add, detail edit, Esc save, complete, delete/undo, command palette, the six-theme matrix, the titlebar theme menu, auto-start, recurrence, the recurrence notice, quick-add parsing, the parse strip's single-row layout at 980px and at 1280px with the inspector open, the tick's reduced-motion end state, write-failure visibility (toggle/delete/undo/load/hard-delete), the trash UI chain (delete → trash visible → restore → main list visible → re-delete → purge with confirm dialog → absent → empty-trash chain), the `deletedAt` field chain, the checklist chain (add / toggle / rename / delete, row progress, recurrence reset, hard-delete cleanup, v1/v2 backup import), the retention boundary table, the focus revision gate (`focusRevisionGate`: main-side counting wrappers on `tasks:list`/`tasks:list-deleted` assert no-change focus pulls nothing, a direct DB write makes focus pull and show the row, and an own UI write's stamp keeps the next focus quiet) and subtask field-level rollback (`subtaskFieldRollback`: a gated `subtasks:update` handler parks a title-only rename while a completed-only toggle passes through to the real DB, then the rename is released to fail — the concurrent `completed` must survive the rollback). Because focus is revision-gated, the read-failure sections (`storageLoadError`, the dual-read block) first create a probe task through the live `tasks:create` channel so the revision actually changes and focus genuinely issues the reads; the probes are cleaned up in the following dismiss/cleared steps. It cleans up its tasks (soft-deleted smoke leftovers are hard-deleted so they cannot pile up in the trash) and restores theme/auto-start. Assertions live in `runSmokeTest()` in `src/main/harness/smoke.ts`; the parser's table-driven and fuzz checks live in `runParseAssertions()` and the retention boundary table in `runRetentionAssertions()` in `src/main/harness/assertions.ts`. The harness entry also refuses to run `POLARIS_SMOKE` when `userData` is not a temp directory (not under `os.tmpdir()` and no `polaris-smoke-` prefix): it prints `POLARIS_SMOKE_ERROR` and exits 1 before any destructive assertion, so a stray env var can never wipe a real profile. Expected values are written as literals, never recomputed through the code under test. The failed-submit path is exercised by dropping the `tasks:create` IPC channel and restoring it with `registerTaskCreate()` — `contextBridge` freezes `window.polaris`, so it cannot be stubbed from the page. The write-failure paths drop `tasks:update` / `tasks:delete` / `tasks:restore` / `tasks:list` / `tasks:delete-forever` one at a time and restore the whole group with `resetTaskIpc()` (remove every `registerIpc`-owned channel — all twenty, including the three trash channels, four project channels, four subtask channels and three tag channels — then call the production `registerIpc()` again — no duplicated zod schemas, `ipc.ts` stays untouched); they assert the error toast's literal copy, the optimistic rollback, the undo toast surviving a failed undo, and clear-on-retry/clear-on-dismiss. Assert end states only: the optimistic "row disappears" is transient and the IPC rejection can roll it back within one poll interval. Height assertions use sub-pixel rects; they were checked **manually** at 100/125/150/200% display scaling and under reduced motion — the harness now emulates 125/150/200% display scaling via CDP `deviceScaleFactor` (`scalingFrameWorks` guards the 56px collapsed quick-add frame and asserts the emulated `devicePixelRatio` took effect); other scaling details (segment widths, 1px separators, inset focus rings, small Chinese text) still lack automated coverage. Two animation-end-state guards do run automatically: `checkDrawn` asserts the tick's final `stroke-dashoffset` is `0px`, and `checkDrawnReduced` attaches the CDP debugger, sets `prefers-reduced-motion: reduce` via `Emulation.setEmulatedMedia`, then creates and completes a fresh task so the tick **remounts** — only a remount exercises the reduce entrance path — before restoring the media features and detaching. Never assert the reduce end-state on an already-mounted node. The verdict is a named `checks` map, not a `&&` chain: a failing run prints `POLARIS_SMOKE_FAILED ["name", …]` on its own line and carries a `failed` array in the JSON. Never triage a red run by filtering the result for `value === false` — `afterAdd`, `afterDelete` and `commandCount` are numeric comparisons and the two version fields are string comparisons, so those failures leave no `false` anywhere in the payload. Cross-process waits go through `waitForCondition()` (bounded poll, returns false on timeout so the run finishes and reports every failure) plus `settledFrames()` (two rAFs before `capturePage`, raced against a 1s cap because an occluded window throttles rAF and would hang the run). **Never poll until the expected colour for a first-frame assertion** — that turns "the reminder paints the right colour on frame one" into a tautology, since a window that paints wrong and then corrects would pass. Wait for readiness (shell + title text), then sample once. Convergence assertions like cross-window theme follow *should* poll for the expected value. The renderer-side `await sleep()` calls are deliberately left alone: several guard debounces and entrance animations, and measuring straight after a condition would catch a mid-animation height.

## Process and data architecture

- `src/main` is the only privileged process. `src/preload/index.ts` exposes a typed `window.polaris`; the renderer runs with `contextIsolation` and `sandbox`, no Node access. `PolarisApi` in `src/shared/types.ts` plus the declaration in `src/renderer/src/env.d.ts` are the contract.
- IPC goes renderer → preload → main, but the handlers live in two places. `src/main/ipc.ts` owns tasks, projects, subtasks and tags and validates every payload with zod; `app:set-theme`, `app:get-version`, `app:get-autostart`, `app:set-autostart`, `app:get-close-to-tray`, `app:set-close-to-tray`, `app:get-global-hotkey`, `app:set-global-hotkey`, `app:get-mcp`, `app:set-mcp`, `app:mcp-token-get`, `app:mcp-token-regenerate`, `data:revision`, `data:export`, `data:import` and `reminder:dismiss` are registered inline in `app.whenReady()` in `src/main/index.ts` and are hand-checked, not zod-validated (`data:revision` is payload-free read-only, like `app:get-version`); the four `update:*` channels live in `src/main/updater.ts` (see Online updates). Adding a data operation means updating `shared/types.ts`, `preload/index.ts`, `main/ipc.ts`, and `main/db.ts` together; adding an app-level channel means `index.ts`.
- Every channel is a renderer-initiated `invoke`, with exactly one push exception: `update:state` (main→renderer update snapshots, see Online updates). The global hotkey and the tray 「设置」 entry do not add channels: `revealAndDispatch()` calls `executeJavaScript` to dispatch fixed-string CustomEvents — `polaris:quick-add` (the same event the `N` key fires, with `detail.forceToday: true`) and `polaris:open-settings` (Sidebar opens the settings panel). `App.tsx` runs `load()` + `loadTrash()` unconditionally on mount; on window `focus` it calls the store's `refreshOnFocus()`, which is **revision-gated**: it fetches `data:revision` (a single-row meta SELECT) and only re-runs `load()` + `loadTrash()` when the number differs from `lastSyncedRevision` (or the fetch fails — fail-open to the old full pull). That is the only refresh path; the reminder window runs `load()` alone. Anything written outside the renderer — a smoke assertion calling `window.polaris` directly, an MCP tool call, a backup import — bumps the revision through migration 7's triggers, so the next focus still pulls and shows it; only the no-change case is skipped (the `tasks` array keeps its reference, zero subscriber re-renders on alt-tab).
- SQLite (`src/main/db.ts`) lives at Electron `userData/polaris.db` in WAL mode, called synchronously from the main process. Tasks are soft-deleted via `deleted_at` into the trash; undo and trash restore both call `restoreTask`. Migrations are sequential `PRAGMA user_version` blocks in `migrate()`; append a new block and never edit one that has shipped. The trash added no migration: `deleted_at` shipped in migration 1. Migration 5 added the `subtasks` table (see Subtasks and checklist). Migration 7 added the **write revision**: meta key `write_revision` starts at '0', and AFTER INSERT/UPDATE/DELETE triggers on all five data tables (`tasks`, `subtasks`, `tags`, `task_tags`, `projects` — 15 triggers named `trg_write_revision_<table>_<op>`) increment it inside the writing transaction. Every write path (IPC/MCP/backup import/retention purge) goes through SQL, so the triggers need zero application-level hooks; cascades bump once per affected row (the number promises monotonic growth, not an exact write count). `meta` itself has no trigger — app settings (theme/locale/tokens) are not task data and must not force a refetch. `getWriteRevision()` reads it (missing/corrupt value → 0, never throws). Triggers are schema, not data: they never enter a backup, and an import target's own triggers bump on the inserted rows.
- `completed_at` (migration 4) records when a task was finished; `updated_at` cannot, because every later edit overwrites it. `updateTask` stamps the transition only: completing sets it, un-completing clears it, re-completing stamps a new instant, and unrelated edits leave it alone. Rows completed before migration 4 stay NULL — the instant was never recorded, and backfilling from `updated_at` would poison any statistics built on it. The column is set by the DB and is not part of `CreateTaskInput`/`UpdateTaskInput`. The completed recurring instance keeps its stamp; the spawned instance has none.
- `listTasks` orders by `completed, has-due, due_at, priority DESC, created_at DESC`. Priority is a tiebreaker **within the same due instant**, not a global sort: tasks the user gave explicit distinct times keep chronological order, while the many tasks quick-add defaults to `todayAt(23,59)` share an instant and therefore sort by priority. Day-granularity grouping stays in the renderer — the DB stores UTC and cannot know the local day.
- App-level settings skip migrations entirely: `getMeta`/`setMeta` read and write the `meta` key/value table created by migration 1. Theme and the `demo_seeded` flag both live there. First launch seeds two projects and eight tutorial sample tasks (one per feature: quick add, subtasks, tags, weekly recurrence, reminder, matrix, completed section; the how-to lives in each task's notes, zh/en mirrored with identical structure), which is the data every screenshot shows.
- All timestamps are ISO UTC strings. Grouping and formatting happen in the renderer (`src/renderer/src/lib/dates.ts`), not in the DB.
- Persistent logging is `electron-log` (`electron-log/main`, a runtime dependency — externalized by `externalizeDepsPlugin` like better-sqlite3). `log.initialize()` runs at the top of `src/main/index.ts`, before any window/DB work; files land in `userData/logs/main.log`, capped at 1MB per file and rotated to `main.old.log` (one archived file, ~2MB ceiling). Both dev and packaged runs write the file; the console transport stays for dev. Production main-process modules (`index.ts`, `db.ts`, `updater.ts`, `mcp.ts`) use `log.*`, never bare `console.*` — packaged stdout goes nowhere, so update failures / DB quarantine must be forensically readable in the file. Milestones are deliberately sparse: startup (version + packaged + userData), auto-backup written, update available/downloaded, MCP listening; errors cover startup failure, unhandledRejection/uncaughtException, DB quarantine (original error + quarantine path), update check/updater errors, MCP listen failure. `autoUpdater.logger = log` routes electron-updater's internal check/download/verify steps into the same file. **The harness's `console.*` calls are the smoke output protocol (`POLARIS_SMOKE_*` lines) — never convert them to electron-log.**

## Subtasks and checklist

- Subtasks are a lightweight checklist, not self-referencing task rows: `subtasks` (`id`, `task_id`, `title`, `completed`, `sort_order`, `created_at`) added by migration 5 (`src/main/db.ts`). They have no due date, reminder, recurrence, project, or priority, and `title` is the only editable text. The parent's completion is independent — checking the task never touches its subtasks, and un-completing leaves them alone.
- `task_id` is `REFERENCES tasks(id) ON DELETE CASCADE`, and `initDatabase()` enables `foreign_keys = ON`, so hard delete, `emptyTrash` and `purgeExpiredDeleted` clean the checklist for free. Soft delete and restore keep the rows (they are only hidden through the parent).
- `listTasks`/`getTask`/`listDeletedTasks` carry two derived counts, `subtaskTotal` and `subtaskDone`, computed by correlated subqueries in `TASK_SELECT`. They are read-only: not in `CreateTaskInput`/`UpdateTaskInput`, not in `BackupTask`, and a missing aggregate maps to 0. `TaskItem` renders the `2/5` badge only when `subtaskTotal > 0`.
- List scaling: `TaskItem` is `memo`-wrapped and subscribes to a boolean `selected` selector (not `selectedTaskId`) plus its single project; `TaskDetail` subscribes to one task via `find` inside the selector. `.task-item` carries `content-visibility: auto` with `contain-intrinsic-size: auto 41.5px` — that estimate is the **content box** (title 21 + gap 4 + meta 16.5); padding/border are added by the box model, so one value yields 67.5px rows in the regular tier and 59.5px in the compact tier. Browser-level windowing skips offscreen paint/layout with zero DOM changes (focus-trap and smoke selectors stay valid); motion exit springs run on the rAF timeline and settle fine offscreen. Smoke seeds 1200 rows (`largeList*` checks) and pins both tiers' placeholder heights. The main-view status bar (`.view-footer`: quick-add/palette hints + version) is `position: sticky; bottom: 0` inside the `.main` scroller (user report: long lists scrolled it out of view): Chrome's sticky-bottom reference lands on the content-box bottom, so offset 0 puts the stuck footer pixel-identical to its in-flow short-content position (zero hop at scroll end); a same-`--bg` box-shadow of `var(--space-6)` covers the padding strip below so rows never show through, and `.main` gets `scroll-padding-bottom: 70px` so keyboard/scrollIntoView never parks a row under the bar. DOM and scroller stay untouched — every scrollTop-based guard keeps its semantics; `mainFooterPinned` seeds 40 rows and pins the footer bottom to `.main` bottom minus paddingBottom at top/mid/end scroll. A conditional scroll-fade (`.view-footer::before`, 40px `linear-gradient(to top, var(--bg), transparent)`, `pointer-events: none`) dissolves rows into the background above the pinned bar only while `.main.can-scroll-down` (scrollTop + clientHeight < scrollHeight - 8, maintained by a passive scroll listener plus ResizeObserver on the scroller and its inner wrapper); at scroll end and short content the fade is off, so resting states and archived screenshots stay pixel-identical, and the same guard pins fade opacity 1 at top/mid and 0 at end. Probe note: occluded windows throttle BeginFrames and freeze CSS transition timelines (fade reads 0 forever) — force frames with `Page.startScreencast` when shooting fade states; foreground users are unaffected.
- Four zod-validated channels in `src/main/ipc.ts`: `subtasks:list(taskId)`, `subtasks:create`, `subtasks:update` (title and/or completed), `subtasks:remove`. `createSubtask` trims, rejects an empty title and a missing/deleted parent (`getTask` filters soft-deleted rows), and appends at `MAX(sort_order) + 1`. `updateSubtask` and `deleteSubtask` are id-scoped; delete is idempotent.
- `SubtaskList.tsx` mounts in `TaskDetail` under the notes. Enter adds and clears for continuous entry (IME-guarded); each row has a checkbox, an inline title input, and a delete button. There is no drag reorder — `sort_order` is insertion order. Renaming commits on blur and Enter. Esc commits the edit but deliberately does **not** `stopPropagation`: it lets `TaskDetail`'s window listener run its existing 「保存并收起」. Blocking it would make Esc in a checklist row mean something different from Esc anywhere else in the inspector.
- The store (`useTaskStore`) keeps `subtasksByTask` separate from `tasks`, updates each mutation optimistically and rolls it back on rejection, and keeps the derived counts in sync through `withSubtaskCounts` until the next `load()` overwrites them from SQLite. `updateSubtask`'s rollback is **field-level** (same shape as `runUpdate`): the pre-call snapshot holds only the keys this patch touched, so a failed rename cannot wipe a concurrently successful `completed` write; the done-count rollback is computed against the store's current row (single-threaded that equals the old `-doneDelta`). Same-field concurrent writes keep the known `runUpdate` residual (later failure restores the pre-A value; the next read corrects it). `addSubtask`/`removeSubtask` deliberately stay row-level: their rollback object is an independent row's insertion/removal, not a field race — the draft is removed by id, the removed row is re-inserted in place with its `sortOrder`, and while a row is absent from the store a concurrent `updateSubtask` finds no entry and returns. `removeTag`'s cascade rollback is already field-scoped (it re-adds only the deleted tag, only on tasks that had it and now lack it). `loadSubtasks` is a third read owner (`'checklist'`), so its failure survives an unrelated successful `load()`; successful writes go through the existing `writeFailed()` path. `deleteForever`/`emptyTrash` drop the cached lists.
- Completing a recurring task copies the subtask titles and `sort_order` to the spawned instance in the same transaction and inserts them with `completed = 0`; the completed instance keeps its own checks. The copies are new rows with fresh ids, so editing either instance never touches the other.
- Subtasks never enter `deriveStats`: completion counts are task rows only, so a checklist step can make the badge read `5/5` while the task itself stays open.
- Backup is `schemaVersion: 3` (v2 added subtasks, v3 added tags/taskTags). `exportBackup()` adds a `subtasks` array to the existing projects/tasks payload; `importBackup()` restores them additively, skipping an id that already exists or whose parent task is absent, and reports `subtasksImported`/`subtasksSkipped`. `backupSchema` accepts `schemaVersion` 1 or 2, makes `subtasks` optional with `.default([])`, and requires only the twelve original task fields — a pre-subtask backup therefore validates and imports unchanged, with an empty checklist. Derived counts are never required in a backup file.
- Smoke: the checklist chain is `subtaskRowProgress`, `subtaskDetailChain`, `subtaskRenamed`, `subtaskPersisted`, `subtaskPurged`, `subtaskRecurrenceWorks` and `subtaskBackupWorks`, all registered in the `checks` map and the result JSON. They seed and hard-delete their own fixtures.

## Tags

- Tags are the second organization dimension alongside projects: migration 6 added `tags` (`id`, `name` UNIQUE, `created_at`) and the `task_tags` join table (composite primary key, both foreign keys `ON DELETE CASCADE`). Deleting a tag cascades its associations; purging a task cascades its links; soft-delete/restore never touches them.
- `Task.tags` is derived by the DB on every read (ordered by name), like the subtask counts — never stored, never in `CreateTaskInput`. The only write path is `UpdateTaskInput.tagIds` through `tasks:update`, with **replace semantics**: the array is the complete target set, omitting it leaves associations alone. `TaskDetail` reads the freshest `task.tags` before computing the next set so a stale frame cannot resurrect a just-removed tag.
- Three zod-validated channels in `ipc.ts`: `tags:list`, `tags:create` (trims; a duplicate name reuses the existing row instead of erroring), `tags:remove` (id-scoped, idempotent). The store mirrors the cascade optimistically on `removeTag` (chips vanish from every row immediately) and restores per-task associations on rollback.
- `tagFilter` and `projectFilter` are mutually exclusive in the store: setting either clears the other and routes to the `all` view. The sidebar renders the tag section only when at least one tag exists; counts are active tasks carrying the tag. The view title becomes `#标签名`.
- Completing a recurring task copies the tag associations to the spawned instance in the same transaction; the completed instance keeps its own.
- Quick-add NLP deliberately has no tag syntax — `#` already means project. Tags are edited in the detail inspector only (input with suggestions, Enter creates-and-attaches, chips remove).
- Backup v3 carries `tags` and `taskTags` arrays; `backupSchema` makes both optional with `.default([])` so v1/v2 files still validate and import. `importBackup` reports `tagsImported`/`taskTagsImported`.
- Auto-backup management (0.16.5): startup auto-backup keeps the latest **21** files (`AUTO_BACKUP_KEEP`, Csv parity; JSON is tiny). Four inline channels in `index.ts` — `backups:list` (metadata only: name/mtimeMs/sizeBytes, newest first, never parses file content), `backups:import` (same size gate + `backupSchema` + `importBackup` merge semantics as `data:import` — additive, never a rollback), `backups:save-as` (copy via `writeFileAtomic` behind the native save dialog), `backups:open-data-dir` (`shell.openPath(userData)`; under `__POLARIS_HARNESS__` it returns `{ opened: false }` without opening Explorer — same lazy convention as splash/updater). The single entry gate is `isAutoBackupFileName()` in `shared/backupNames.ts` (anchored regex on the hyphenated-ISO name; rejects separators/`..` before any `join`), truth-tabled in both `runBackupNameAssertions()` and `verify-pure.mjs`. Settings UI: the accordion toggle lives **inside the backup group-label row** (right side, `.settings-group-label--split`) so the collapsed state adds zero height — the one-screen guards measure collapsed; the body (desc + list with per-row Import / Save as) renders only when expanded, the list caps at 224px with its own scroll, and closing the panel resets the toggle (list cache survives). Rows carry `data-backup-name` for smoke targeting. ## Local MCP service

- `src/main/mcp.ts` is the sole owner of the MCP endpoint, mirroring the hotkey module's intent/state split: meta `mcp_enabled` records the user's choice (**default off**, opt-in — only an explicit '1' enables), `running` records the actual listen state, and a port conflict leaves the switch on with a Chinese `error`. `initMcp()` runs in `app.whenReady()`, `disposeMcp()` in `will-quit`.
- Transport is the stateless subset of MCP Streamable HTTP (2025-03-26): POST `/mcp` carries JSON-RPC (initialize / ping / tools/list / tools/call; notifications get 202), GET gets 405 (no SSE stream), other paths 404. Bound to **127.0.0.1 only**, port 3737, and every POST must carry `Authorization: Bearer <token>` (see the token bullet below) — loopback alone is no longer the trust boundary.
- Bearer token lifecycle: `sk-` + `crypto.randomBytes(32).toString('hex')` (67 chars, entropy unchanged), generated on **first enable** (`apply()` calls `ensureToken()`, so autostart-restore covers it too) and persisted in meta `mcp_token` — restarts keep it, a client configures once and it stays valid. Legacy bare-64-hex tokens from ≤0.16.1 keep authenticating (shape check accepts both, no forced client break); only new generations carry the prefix. A corrupted meta value (neither shape) is treated as absent and regenerated, never used as a credential. `getMcpToken()` reads-or-creates; `regenerateMcpToken()` invalidates the old token immediately. Two inline channels in `index.ts`: `app:mcp-token-get` / `app:mcp-token-regenerate` — both payload-free (like `app:get-version`), exposed as `app.getMcpToken` / `app.regenerateMcpToken`. Settings UI: the token lives **inside the MCP section** as a flex-stretched box showing an **adaptive short mask** (user decisions 2026-11-19: 15:33 min head/tail 4, 16:2x fill the box: `maskToken(token, k)` in SettingsPanel renders `sk-` prefix + head k hex + … + tail k hex, k recomputed from the box width by a ResizeObserver using the mono 0.6em advance and clamped [4,32]; legacy bare tokens take head/tail k of the whole string; the middle never renders; at the unified two-column box cap (~210px) k≈12 so 40 of 64 hex stay hidden; box height constant one nowrap line; clipboard copy still yields the full string), sharing one row with copy / reset right-aligned (`.mcp-token-row` flex + `.mcp-token-actions` `margin-left: auto` — one row shorter than the mask-owns-a-row era); the box **stretches with `flex: 1` to fill the row's remaining width** so the row is justified edge-to-edge — box flush against the card's left edge, button group flush right (user decision 2026-11-19 16:17, reverting the 15:4x equal-width mirror which left a dead gap mid-row; `min-width: 0` + ellipsis guard ultra-narrow cards), renders only when enabled; the usage note lives in the reserved single-line feedback slot (`.mcp-token-slot`: default text = `settings.mcpTokenDesc`, transient notices replace it for 2.6s, overlong text ellipsized with the full string in `title`) so the block contributes no conditional rows; clipboard copy and reset behind the shared `ConfirmDialog` (old client configs die — destructive, so it confirms; the dialog's React-root Esc stop keeps the settings panel open). **Breaking for existing MCP clients**: configs from the no-auth era must add the Bearer header; README says so explicitly.
- Request rejection matrix, in order: any request carrying an `Origin` header gets **403** (proof of browser origin — legit CLI/desktop MCP clients send none); `Host` must be a loopback literal with the listening port (`127.0.0.1:3737` / `localhost:3737` / `[::1]:3737`), otherwise **403** (DNS-rebinding defense: `evil.example` resolved to 127.0.0.1 still sends `Host: evil.example:3737`); POST must declare `Content-Type: application/json`, otherwise **415 without reading the body** (a `text/plain` "simple request" skips the CORS preflight and is the only blind-write/CSRF channel); then the Bearer check — missing header, wrong scheme or wrong token gets **401** (`WWW-Authenticate: Bearer`, body unread). Comparison hashes both sides with SHA-256 and `timingSafeEqual`s the fixed-length digests: no length short-circuit, no timing side channel. GET/404/405 semantics run before auth and leak nothing. Body is capped at 1MB.
- The eight tools (list_tasks / get_task / create_task / update_task / complete_task / delete_task / list_projects / list_tags) call the existing `db.ts` functions directly — recurrence spawning, soft delete, `completed_at` stamping and tag replace-semantics are identical to the UI with zero logic duplication and no second SQLite connection. Tool arguments are zod-validated against the same constraints as the `ipc.ts` front door (title non-empty ≤500, notes ≤20000, `dueAt` must pass `Date.parse`, priority integer 0–3, tagIds ≤50 non-empty strings) — invalid input is rejected, never silently truncated/clamped. Tool errors return as `isError: true` tool results, not JSON-RPC errors (per MCP spec); malformed JSON-RPC gets -32700/-32600/-32601.
- The service lives and dies with the app — tray-resident autostart is the normal state.
- Smoke: `mcpWorks` enables via the production `setMcpEnabled`, polls `getMcpState().running`, fetches the token through the real IPC channel (`window.polaris.app.getMcpToken()` in the renderer), then drives real HTTP with the Bearer header: initialize serverInfo, tools/list count (8), create → list → complete round-trip, GET 405, the Origin/Host/Content-Type rejection matrix, token shape + read stability (sk- + 64 hex, two gets equal), and connection-refused after disable. `mcpAuthRejects` pins the 401 matrix (no token / wrong token / non-Bearer scheme); `mcpTokenRegenerate` regenerates through IPC and asserts old token 401, new token initialize 200 (the bad-priority zod probe runs after regeneration, proving the new token also serves tools/call). Cleans up its fixture and restores meta to off (the token itself persists by design). All registered in the `checks` map and the result JSON.

## Cloud drive backup (L0)

- `src/main/mirror.ts` is the sole owner, mirroring mcp.ts's intent/state split: meta `cloud_mirror_enabled` / `cloud_mirror_folder` / `cloud_mirror_last` / `cloud_mirror_error` record user intent and the last outcome (**default off**, zero migrations — everything lives in the existing meta table). Write-only and zero network code: the upload is done by the user's own cloud-drive client syncing the chosen folder, never by Polaris.
- The write gate is the pure `shouldMirror()` in `src/shared/mirror.ts` (same paradigm as `shouldAutoCheck`): enabled + dirty + non-blank folder + minimum gap since the last attempt (production 30s, tests inject via `setMirrorMinGapMs`). Clock rollback, NaN timestamps and invalid gaps all pass the gate — better an extra snapshot than a mirror frozen forever by one clock change. Its truth table is maintained in duplicate in `runMirrorAssertions()` (harness) and `verify-pure.mjs` — **both copies must be updated together**.
- A 1s tick does a single meta SELECT; write-revision changes mark dirty. The snapshot reuses backup serialization (`schemaVersion: 3`) and is written atomically to `<folder>/latest.json`, rolling overwrite. The revision is read before serialization so a concurrent write biases toward an extra snapshot, never a missed one. Folder guard rejects userData itself, its children, or its parents (realpath + case-insensitive comparison on Windows) — the live `polaris.db` must never enter sync scope. An unavailable folder pauses the mirror silently: the switch stays on, a localized error lands in the status line, and the app keeps working fully.
- Recovery guard: a fresh install whose library is still demo-only (`isDemoOnlyLibrary()` against the seed-id manifest) pointing at a folder that already has `latest.json` holds writes until the user restores or real data appears — the first snapshot must not overwrite the only cloud history with tutorial samples. `mirror:import-from-cloud` merges by ID and can clean the demo seed rows after a restore.
- IPC channels `mirror:get-state` / `mirror:set-enabled` / `mirror:set-folder` / `mirror:import-from-cloud` live inline in `index.ts` (hand payload checks, same style as `app:set-mcp`); the folder picker pre-fills `%OneDrive%\PolarisSync`. Exposed as `window.polaris.mirror`.

The MCP token's "仅存本机" wording is deliberately unchanged: the token lives in meta and never enters snapshots. `settings.cloudMirrorPrivacy` must say the snapshots do reach the cloud via the user's own client — Polaris itself never goes online or uploads.

## Recurrence and reminders

- Recurrence rules are RFC 5545 strings executed by `rrule` in `src/shared/recurrence.ts`. `rrule` treats a Date's UTC fields as a floating wall clock, so the code converts local wall time in and out (`toWallTime`/`fromWallTime`) to keep 18:00 at 18:00. COUNT and UNTIL are rejected. The monthly preset clamps 29–31 to the last day of short months (`nextMonthlyClamped`).
- `nextOccurrence(dueAt, rule, now)` (clock injectable) anchors at the **later of due and now in wall-clock space** and calls `rule.after(anchor, false)` to jump straight to the first candidate — it no longer iterates from due with a 1000-step cap, so a daily task overdue by 3+ years no longer silently breaks the chain. The only loop left advances at most 3 steps and exists solely for DST fall-back ambiguity (the wall→instant read-back can land before now); it is unrelated to how overdue the task is. **Month-end semantics currently fork**: the `FREQ=MONTHLY` preset takes the clamp path (Jan 31 → Feb 28), while custom rules like `FREQ=MONTHLY;INTERVAL=2` go through rrule and skip short months entirely (sequence 1/3/5/7/9/11). This fork is pinned by truth-table literals, not fixed — unifying it awaits a product decision.
- Completing a recurring task is one transaction in `updateTask`: the completed instance keeps its history but loses its rule, and a new active task is inserted with the next due date plus the same project, priority, notes, and rule. A reminder is inherited as an offset before due, only when that offset is 0–7 days. Subtask titles and `sort_order` are copied to the new instance in the same transaction with `completed = 0`; the completed instance keeps its own checks. Un-completing does not remove the spawned task.
- Changing `remindAt` clears `reminded_at` in `updateTask`, and `listDueReminders` re-fires whenever `reminded_at < remind_at` — that pair is how moving a reminder re-arms it. `toggleTask` in `db.ts` just forwards to `updateTask`, so the checkbox path spawns recurrence too.
- Reminders (`src/main/reminders.ts`) use a 30-second interval, a one-shot check 4 seconds after startup, `powerMonitor` resume, a queue, and one custom frameless BrowserWindow at the bottom-right. `reminded_at` is written only in `ready-to-show`, so a failed load or a quit leaves the reminder pending. Missed reminders fire on the next launch. Reminders only work while Polaris is running (closing the window keeps it in the tray).
- The reminder window loads the same renderer at `#/reminder/<taskId>`; `src/renderer/src/main.tsx` switches to `ReminderView` from that hash.

## Trash and retention

- `src/shared/retention.ts` is the single authority on automatic cleanup: `TRASH_RETENTION_DAYS = 30` and `isPurgeable(deletedAt, now)` — null and unparseable timestamps return false (keep, never mis-delete), and a row is purgeable once `now - deletedAt >= 30 days` (epoch-ms comparison, clock injected). `db.purgeExpiredDeleted(now)` SELECTs the soft-deleted rows and asks `isPurgeable` per row in JS, then DELETEs by id in one synchronous transaction — no SQL cutoff that could drift from the user-written function. `runRetentionAssertions()` pins the boundary (null / 29d / exactly 30d / ±1ms / invalid / future / a second injected clock) with literal expectations.
- Purge runs at two points: startup right after `initDatabase()`, and inside the `tasks:list-deleted` handler before listing — so the trash the user sees never contains an expired row. There is no background timer.
- Three channels, all in `registerIpc()` (and all in `resetTaskIpc()`'s hardcoded array): `tasks:list-deleted` (purge then list), `tasks:delete-forever` (idempotent `DELETE … WHERE id = ? AND deleted_at IS NOT NULL` — a live task can never be destroyed through it; no existence check, because `getTask` filters deleted rows out and cannot answer "is this in the trash"), `tasks:empty-trash` (one atomic `DELETE … WHERE deleted_at IS NOT NULL`). These were the repo's first DELETE statements; `subtasks:remove` is the fourth and `tags:remove` the fifth. All three task deletions rely on `ON DELETE CASCADE` to clear the parent's subtasks, so no explicit child delete is needed in the purge paths.
- Store separation is load-bearing: `trashedTasks` never merges into `tasks` (it would leak into sidebar counts, the progress ring, palette search and the inspector), and `loadTrash()` never merges into `load()` — `ReminderView` mounts through the same `load()`, and `list-deleted` carries a purge write, so merging would hard-delete rows on every reminder popup and let a trash read failure paint the main window's 「读取本地数据失败」. Read errors carry a failure set (`load` / `trash`): each read's success removes only its own mark and the toast clears only when the set empties, so a double failure survives until both reads succeed (a single slot would be overwritten by the later failure, losing the earlier evidence); any write outcome or manual dismiss clears the whole set.
- Two-way sync: `removeTask` optimistically inserts the row into `trashedTasks` (approximate `deletedAt`, replaced by the DB stamp on the next `loadTrash`), and rolls it back on rejection; `undoDelete` removes it on success. `deleteForever`/`restoreFromTrash` clear a `pendingDeletion` pointing at the row; `emptyTrash` clears it unconditionally — otherwise 「soft-delete → empty → Ctrl+Z」 would fire an undo that can never succeed — and on rejection rolls back both `trashedTasks` and the cleared `pendingDeletion`. Trash restore is silent (no toast; only destructive actions get one) and reuses `tasks.restore` unchanged, so a restored overdue task re-arms its reminder (accepted).
- View wiring: `AppView` includes `'trash'`; `setView('trash')` clears the selection and calls `loadTrash()`; selecting a live task from the palette leaves the trash for 「全部任务」. The trash mounts no QuickAdd — `N` / palette 「新建任务」 / the footer hint all route through `polaris:quick-add`, which jumps back to 「今天」 and focuses the input. The header hides the progress ring and search, showing only 「清空回收站」 (disabled when empty). `TrashItem` has no checkbox and no detail entry (soft-deleted rows throw 「任务不存在」 on update/toggle); actions are always visible. `ConfirmDialog` (purge + empty share it) sits on the focus-trap stack, defaults focus to 取消, stops Esc propagation, closes on `paletteOpen`, and uses the danger *tint* — there is no solid red fill anywhere in the app. Its state lives in the store (`trashConfirm`): while open, the global `N` and Ctrl+Z shortcuts stand down and `setView` clears it, and `aria-describedby` reads the full warning to screen readers.
- Smoke: the trash chain hard-deletes smoke-prefixed leftovers first (earlier sections' `tasks.remove` only soft-deletes), asserts end states through the false-returning `waitFor`, dispatches `focus` after API writes, and self-cleans its fixtures with `deleteForever`/`emptyTrash`. The confirm dialog is the ghost scan's fifth state. Regression guards for the five review fixes: `storageDualReadError`/`storageDualReadCleared` drop both read channels, then let only the trash read succeed — the error toast must survive until both reads succeed; `confirmBlocksN`/`confirmBlocksUndo` dispatch N and Ctrl+Z while the purge confirm is open and assert the view, the panel, the trashed row and the undo toast are untouched; `confirmDescribedBy` checks the panel's `aria-describedby` resolves to the literal warning copy; `trashFocusLands` asserts focus ends on `.main` or a neighbor's `.trash-restore` (never `body`) after a confirmed purge's exit settles; `storageEmptyError`/`storageEmptyClears` drop `tasks:empty-trash` and assert the failed empty rolls back the row *and* restores the undo slot, then a retry empties and clears it.

## Quick-add parsing

- `src/shared/quickAddParse.ts` is a pure function (no React, no DOM, no Node) shared by the renderer and the smoke assertions. `parseQuickAdd(raw, { now, projects, dismissed })` returns the title, `dueAt`, `projectId`, `priority`, the token spans, the chips and the screen-reader announcement. `now` is injected so tests can pin the clock.
- The pipeline is fixed: length-preserving normalization → marker scan (`#project`, `!priority`) → mask table + guards → overlap resolution → punctuation merge → head/tail anchoring → slot merge → time layering → title. Read the step comments before changing any stage; the order is load-bearing.
- Chinese has no word boundaries, so `\b` and lookbehind are useless. Precision comes from the mask table, the character guards, and anchoring: a date is only consumed when it touches the start or the end of the string. Widening the grammar without widening the masks will eat words out of titles.
- Offsets are UTF-16 code unit indices into the raw string, half-open. They feed both `String.slice` and `setSelectionRange`. Switching to code point counting misaligns the caret and the title.
- Never derive weekday or digit values with `indexOf` on the character sets: `WD` has eight characters for seven weekdays and `ZH` has both `零` and `〇`. Use the explicit `DOW_IDX` / `ZH_DIGIT` maps.
- The input's value is never rewritten. Dismissing a chip records `key -> recognizable candidate count` (`parse.candidateCounts`) in `dismissed`; `pruneDismissed` releases a key once the text stops occurring that many times. Counting raw substrings instead would let a guard-rejected occurrence inflate the count and resurrect a cancelled date when the user edits the title. Both functions are identity-preserving so they can be used inside `setState` without a render loop. Prune only in handlers that change `parseText`, never in an effect that depends on `dismissed`.
- A token's key uses its core span, never the punctuation merged around it, so typing a `。` beside a cancelled `#工作` does not resurrect the chip. Dismissal is re-checked after the merge. Markers — including ambiguous duplicates — are masked regardless of dismissal, which is what lets the tail anchor see through a cancelled `#项目` and stops a duplicate project named `明天` from being eaten as a date.
- Project names are normalized on both sides of the comparison; a project legitimately named `项目１` must match `#项目1`.
- The clock is read through one `readNow()` helper shared by the preview memo and `submit()`. Two clock sources is how a chip promises a date the saved task never gets. `readNow()` prefers `window.__polarisParseNow` — the smoke clock hook declared in `env.d.ts`, set and deleted by `runSmokeTest` — over `new Date()`. A 60-second `nowTick` re-parses so relative dates stay honest while the input sits idle.
- A module-level `draftCache` in `QuickAdd.tsx` holds the raw text and the dismissal map, so a view switch that unmounts the component does not lose the draft.
- `focusAfterDismiss` decides from `parseRef`, not a DOM query: `AnimatePresence` keeps the exiting strip's buttons mounted, so a query would focus a node that unmounts milliseconds later and strand focus on `<body>`.
- Overlap tests use `overlapIndex` (sorted spans + prefix-max binary search) and anchoring uses start/end maps. The naive `.some(overlaps)` and `.find` scans are quadratic, and parsing runs on every keystroke.
- `formatParsedDue` in the same module is the app's only due-date formatter; `lib/dates.ts` `formatDue` delegates to it. Keep it that way so chips, rows, detail, palette, reminder and the submit receipt cannot disagree.
- IME: `compositionstart` freezes `parseText`, `onChange` still updates the controlled value, and the keydown guard checks `isComposing`, `keyCode === 229`, the composing ref and a 30ms post-composition grace window. Removing any of the four reintroduces mid-composition submits.
- Esc is handled on `.quick-add-shell` and must `stopPropagation`: `TaskDetail` listens on `window` and would otherwise close the inspector instead of clearing the draft.
- The frame lives on `.quick-add-shell` with `min-height: 56px`, not on `.quick-add`. Under fractional display scaling a 1px border snaps to a sub-pixel used value, so a fixed row height alone would not reproduce the 56px collapsed frame. Measure with `getBoundingClientRect`, not `offsetHeight`.

## Date/time picker

- Never use `<input type="datetime-local">`. Chromium's picker is an OS-level popup outside the page DOM: it cannot be styled, and clicking it counts as an outside click that closes the popover. `DateTimePicker.tsx` + `lib/dateTime.ts` replace it.
- The picker lives inside the existing `.detail-popover` (280px, cap 420px). The month grid is always 42 cells so paging months never changes the height and fights the repositioning. Presets are `.detail-chip` rows, not a vertical list — five stacked reminder presets plus a calendar cannot fit 420px.
- Day cells are `div[role="gridcell"]`, not buttons: `useFocusTrap`'s FOCUSABLE selector counts buttons regardless of `tabindex`, so 42 buttons would pollute the narrow-screen trap. Only the roving cell carries `tabindex="0"` and `data-popover-focus`.
- Popover effects key on `popoverKind`, never the `popover` object. Repositioning creates a new object; re-arming the 30ms initial-focus timer would steal focus from the minute field or the confirm-clear cancel button.
- There is one commit path, and it reads the instant back (`draftFrom(draftToIso(next))`). That keeps the display, `aria-valuenow` and the stored row identical across a DST gap. `TimeField` keeps its own typing text and clears it on `resetKey`, so a half-typed digit can never be shown while a different value is stored.
- Blur discards an incomplete digit prefix; Enter and `:` are explicit confirms and do commit a single digit. Both typing and blur gate on `isComplete` in `lib/dateTime.ts` — keep that predicate shared. Committing on blur instead lets a real mouse click on ±15 (mousedown blurs the field first) step from the wrong hour, while a programmatic `.click()` in smoke skips blur entirely and hides it. `pickerBlurKeepsHour` covers the real blur path.
- Field arrows wrap within the field; ±15 (buttons or Shift+arrows) clamps within the day; only the calendar changes the date. The ±15 buttons are real tabbable controls with `aria-label` and a keyboard equivalent.
- `laterToday` rounds up to the next 5-minute mark. When the rounding crosses midnight it clamps to today 23:59 — **except during the day's final minute**, where 23:59 is itself behind us and the answer moves to tomorrow 00:00. Clamping unconditionally was the bug: for 60 seconds every day 「今天」 produced a task that was overdue the moment it was saved. `pickDay` re-focuses the calendar on the returned day, so the rollover is visible.
- The contract is checked on the **instant the draft reads back to**, never on the wall-clock digits. Rounding produces an instant, but splitting it into hour/minute and refilling is lossy: in a DST fall-back the same wall time occurs twice and `withTime` resolves to the earlier one (New York, up to an hour early), and in a zone that rolls back at midnight the wall clock moves backwards inside the same day, so 23:59 computes as 23:00 (Santiago, 59.5 min early). `laterToday` therefore reads the candidate back through `draftToIso` and, while it is not strictly after `now`, keeps advancing along the real time axis in 5-minute steps (288-step guard = a full day). A `Draft` cannot express the second occurrence of a repeated hour, so skipping past the ambiguity is the only honest answer. Never reintroduce a wall-clock-only comparison here.
- `verify:datetime` sweeps 5760 real instants on a fixed day **plus** every 2026 DST transition in seven zones (New York, Santiago, Havana, Lord Howe, Chatham, London, Shanghai as the DST-free control). Transitions are **discovered** by an hourly `getTimezoneOffset()` scan, not hardcoded, and the sweep steps by epoch — wall-clock construction structurally cannot reach the second occurrence of a repeated hour. Node honours a runtime `process.env.TZ` change, so one process covers every zone. One known gap remains: during 23:59 the today *cell* also bounces to tomorrow and −15 is disabled at 00:00, so the mouse cannot get back to today. The smoke's `pickerTodayFuture` reads the clock **before** the click and allows the next day when either end of the click window is inside 23:59; reading it after left a ~0.5s false-failure window around midnight.
- Moving a due date moves the reminder by the same offset in one patch, otherwise a far-out deadline silently drops the reminder on the next recurrence.

The splash reads the query, **not** localStorage: main's meta record is authoritative and the splash origin may differ from the main renderer's. It reuses globals.css tokens plus `.aurora`/`.noise` and the `spin` keyframe; the page is a CSS-only launch animation (converging light points → star ignite + one-shot pulse → orbit ring with a traveling signal dot → wordmark tracking settle, ~2s, no JS animation, no deps) whose rules are the `/* ---------- splash ---------- */` section of globals.css, and `src/renderer/src/splash.ts` only imports fonts + that stylesheet (no React, no IPC). The orbit spin is the animation's only loop — it keeps waiting when init is slower than the sequence. `openSplashWindow` runs before `createWindow()` and never blocks init; `revealMainWindow` (called from main's `ready-to-show`, a real main-frame `did-fail-load` — errorCode −3 ABORTED is ignored — and `showMainWindow` while the splash is up) waits out a 2000ms minimum visibility so the ~2s animation settles before handoff, shows the main window, keeps the splash `alwaysOnTop` and fades it over 200ms with `setOpacity`, then destroys it; a 12s failsafe reveals even if the renderer never loads, and a splash that never painted is destroyed instead of faded. Skipped entirely under `--hidden` and all three harness envs, so smoke and screenshots stay deterministic.

## Global hotkey

- `src/main/hotkey.ts` is the only owner of `globalShortcut`. Accelerator `Control+Alt+P` (`GLOBAL_HOTKEY_LABEL` is the human label `Ctrl+Alt+P`), state in the existing `meta` table under `global_hotkey` — no migration. Absent means enabled; only an explicit `'0'` turns it off. `initGlobalHotkey()` runs in `app.whenReady()` after `createWindow()` / `createTray()` / `startReminderScheduler()`, and `app.on('will-quit')` calls `disposeGlobalHotkey()`; do not register the accelerator anywhere else.
- `enabled` (what the user wants, persisted) and `registered` (what actually happened, memory only) are separate. A taken accelerator leaves `enabled: true`, `registered: false` and a Chinese `error`; the rest of the app is unaffected. `setGlobalHotkeyEnabled()` writes meta first and then applies, so toggling off/on retries registration. Read `registered` from the module, never `globalShortcut.isRegistered` — the smoke test occupies the accelerator in the same process, and that query would report the test's registration as ours.
- The hotkey trigger is `revealQuickCapture()`, a thin wrapper over the shared `revealAndDispatch(script)`: `showMainWindow()` (which already covers a hidden/minimized window and the `--hidden` start-to-tray path), waits up to 3s for `did-finish-load` if the renderer is still loading, then `executeJavaScript` dispatches a fixed-string CustomEvent. The hotkey sends `polaris:quick-add` with `detail.forceToday: true` — `TaskView`'s existing listener switches to 「今天」 and focuses `.quick-add input`; the `N` key keeps its old behavior because it sends no detail. The tray 「设置」 entry uses the same helper via `revealSettings()`, dispatching `polaris:open-settings`, which `Sidebar` listens for to open the settings panel (clearing any stale `scrollTo` target). Do not add a second focus/reveal path or a new IPC channel for either.
- `GlobalHotkeyState { enabled, registered, accelerator, error? }` is in `shared/types.ts`; the settings row's description swaps to the conflict error (`.settings-row-desc.is-error[role=alert]`, single-line ellipsis + full text in `title`) when enabled-but-registered-false — zero extra rows; the panel fits every tier without scrolling (`settingsNoScrollMcp`).
- Smoke cannot press a real global shortcut, so it checks the parts that are observable: `hotkeyDefaultOn`, `hotkeySettingsRoundTrip` (switch IPC round trip + meta `'0'`/`'1'` + `isRegistered`), `hotkeyConflictDegrades` (register the accelerator from the test, then assert the Chinese error and that the switch stays on), `hotkeyWakesAndFocuses` (switch to 「统计」, hide the window, call `revealQuickCapture()`, assert visible + 「今天」 + focused input).
- Tray-menu smoke runs right after `trayToggleWorks` and **before** the synthetic update snapshots (so `noDialog` is provable on a clean renderer): `trayMenuEntries` (built menu labels are exactly 打开 Polaris / 设置 / 检查更新 / 退出), `traySettingsOpens` (hide the window, call the real `revealSettings()`, assert wake + panel opens + closes), `trayCheckFeedback` (pure `describeTrayCheck` table over all seven states — message copy and `surface` flag), `trayCheckSilent` (hide the window, call the real `checkUpdatesFromTray()` in dev = unsupported, assert the window stays hidden and no `.update-panel` appears).

## Renderer

- `useTaskStore` writes optimistically and rolls back on rejection: `updateTask` restores the previous task and rethrows, while `removeTask` and `toggleTask` log and swallow. Every catch also writes `storageError` (a fixed Chinese message — writes get 「保存失败，改动未写入本地数据库」, reads get 「读取本地数据失败」), and the next successful read/write clears it — except that read failures carry an owner (`load` vs `loadTrash`), so one read's success cannot erase the other read's failure evidence; the sidebar's 「自动保存」 promise is why no write failure may stay console-only. The trash actions (`restoreFromTrash`/`deleteForever`/`emptyTrash`) roll `trashedTasks` back on rejection and keep `pendingDeletion` coordinated (see Trash and retention). `UndoToast` renders `storageError` as a `role="alert"` toast that never auto-dismisses — it leaves only via its 关闭 button or the next success — stacked above the undo/notice toast rather than taking their slot, so a failed undo shows both the error and the retry affordance. `toggleTask` no longer calls `load()`: `runUpdate` inserts the DB-authoritative `spawned` row from the `tasks:update` result directly (dedup-guarded) and raises the 「已创建下一次」 notice from its `dueAt` — no title+rule heuristic, no full refetch.
- Revision stamping (`lastSyncedRevision`): `load()` fetches `data:revision` **before** reading the lists and stamps that number on success — direction is load-bearing: a write landing between the fetch and the list read makes the current number newer than the stamp, so the next focus over-pulls (never under-pulls); fetching after the list would stamp a number containing gap writes onto a snapshot that lacks them and the gate would miss them forever. A failed revision fetch stamps `null` (always-pull). Concurrent `load()`s are sequenced (`loadSeq`): only the latest-issued load applies data and stamp, stale successes/failures are dropped. Every successful store write (tasks/subtasks/tags/projects/trash pipelines) then fire-and-forget refreshes the stamp (`stampRevision`) so the next focus does not re-pull for the app's own write; failure paths never stamp. Missed stamps cost at most one extra pull — correctness rests on "different number ⇒ pull". Known inherent boundary (same class as `runUpdate`'s same-field residual): an external write landing in the millisecond gap between an own write's commit and its stamp fetch is included in the stamped number but not yet in the store, so it surfaces on the next focus after any later change; closing it fully would require every write channel to return its settled revision.
- No router. `useTaskStore` (Zustand) owns tasks, projects, view, project filter, selection, and palette; `TaskView` derives the visible and completed lists. `TaskDetail` is a 360px third grid column at ≥1180px (`role="region"`, no focus trap) that collapses to 0px with a 220ms grid transition when no task is selected, and a 400px modal sheet below that (`role="dialog"`, trap). `CommandPalette` and `SettingsPanel` remain traps; `useFocusTrap` maintains a trap stack so overlapping overlays do not fight over Tab.
- The completed section is **collapsed by default** in every view that has one (today/upcoming/all/completed, including project/tag-filtered variants — everywhere `completedForView` covers; Matrix/Calendar/Stats are untouched). A single `.completed-toggle` button styled like the old section label reads 「已完成 {count} 条」 / "{count} completed" (`views.completedToggle`, tabular-nums count, chevron rotates with `aria-expanded`), with `aria-controls` pointing at the always-mounted `#completed-task-list` container whose rows conditionally mount — collapsing unmounts rows, it does not hide them visually. The state is component-local `useState(false)`, never persisted (every launch starts collapsed), and resets to collapsed on view/project/tag-filter switches. Completing a task never auto-expands the section (no focus stealing): the row exits the active list and only the count ticks up; un-completing while expanded returns the row to the active list through the existing optimistic path. At N=0 the whole section stays unmounted, as before. `TaskItem`'s delete-focus fallback chain is sibling row → quick-add input → `.main` (the completed view mounts no quick-add, so deleting the last expanded completed row must not drop focus to body). Smoke steps that assert on completed-row DOM (`done`/`checkDrawn`, `checkDrawnReduced`, `storageErrorClears`, `completedAtShown`, `largeListOffscreenToggle`, the main-block delete) expand the section first via the shared `expandCompleted()`/`collapseCompleted()` page helpers; `completedCollapsedByDefault` pins the whole chain (hidden at zero → collapsed check increments without expanding → expand shows `.done` rows → collapse unmounts → view switch resets).
- Task detail autosaves title and notes with a 500ms debounce, flushes on blur/Esc/task switch/close/unmount, and serializes saves per task. Deadline, reminder, and recurrence are human-readable rows with anchored popovers; project and priority stay inline for one-click edits. The checklist is the bottom block (`SubtaskList`): its add input is outside the autosave, its row edits are immediate store mutations, and its progress reads the task's derived counts, not the local list length.
- Theme bootstrapping happens twice on purpose: the inline script in `src/renderer/index.html` sets `data-theme` before first paint, then `useThemeStore`/`ThemeSync` keep it in sync and notify the main process. The localStorage key is `polaris-theme`; the inline script and `isAppTheme` accept the six registry ids, and an unknown stored value falls back to the system preference.
- The displayed version comes from `app:get-version` via `useAppVersion` — one fetch per session shared by the footer and Settings, empty on failure. Never hardcode a version string in the renderer; bump `package.json` only.
- Accessibility is part of the design system: keep `MotionConfig reducedMotion="user"`, visible focus rings, focus traps with focus restoration, `aria-hidden` on decorative icons, and labels on icon-only controls.
- Status copy states static facts only. Data locality is 「任务数据仅存本机」 — the subject is the *task data*, not the app, because update checks do go online. The sidebar `.sidebar-storage` fact card (HardDrive icon, subtitle 「自动保存 · 点击备份」) is the single home of this sentence and is a button: it opens Settings scrolled to the backup section (`scrollTo='backup'` prop, scroll after the entrance spring settles), turning the privacy promise into an exit — export anytime. The Settings footer no longer repeats it. The titlebar carries no DB status. Smoke `storageCardWorks` shrinks the window to force panel overflow, clicks the card, and asserts the backup actions land inside the panel viewport, the footer carries no duplicate sentence, and a normal Settings reopen stays at the top. Never introduce 「已连接/保存中/已保存」 live indicators: main-process SQLite is synchronous, optimistic writes expose no intermediate state, and `removeTask`/`toggleTask` swallow failures, so any such lamp would be fabricated. A real save-failure surface must first wire the actual rollback paths into the store, then ship copy — never the reverse.
- A focus ring must never be the same colour as the surface it surrounds — that reads as a ghost copy of the control, not as focus. Controls filled with `--accent` take `--on-accent` at a negative offset (ring inside the fill); controls already bordered with `--accent` drop the border while focused. The grouped rule sits directly under the global `:focus-visible`; add new accent controls to it. `runSmokeTest` scans every focusable element in five UI states (main view, inspector, date popover, expanded theme menu, confirm dialog) and fails on any ring that matches its own fill or border, and on any inset shadow over an accent fill — the selected-and-today calendar cell must drop its inset today ring (`.dp-day.is-selected.is-today { box-shadow: none }`), same as the preview-and-today cell. Inside the `executeJavaScript` template literals, regex backslashes must be doubled (`\\(`): a single one is cooked away by the template, the page-side regex loses its literal parens, `rgbOf` returns NaN components and every colour comparison silently no-ops — the scan then passes vacuously.
- CSS variables are `--surface-1` / `--text-secondary` style, not the `--surface1` shorthand used in the design references. An undefined `var()` with no fallback silently renders transparent; the smoke suite's CSS is checked for this.
- `--inner-highlight` is a bevel for translucent glass surfaces only: it is 4.5% white in the dark-family themes (夜阑/暮蓝/松墨) but **90% white in the light-family themes (昼白/暖砂/天蓝)**. Never put it on a saturated `--accent` fill — measured over the reminder button it produced `rgb(231,242,241)` along the top edge, a near-white rim that reads as a second outline. Accent-filled controls are flat: no inset shadow at all. The smoke suite flags any inset shadow on an accent fill and pixel-samples the reminder button's top edge in each theme.
- When diagnosing a visual defect, reproduce the user's actual state. Forcing focus to make a symptom appear proves a different bug: the reminder button's ghosting was an inset bevel visible while unfocused, not the focus ring.
- Styling is one stylesheet, `src/renderer/src/styles/globals.css`, using Tailwind v4 `@theme` plus CSS variables for all six themes. There is no `tailwind.config.*`. Prefer existing tokens (`--text-*`, `--surface-*`, `--accent`, spacing and radius variables) over raw values. Both renderer entries (`index.html` and the splash's `splash.html`) import it, so `verify:themes` covers splash colors and var() references automatically.
- For UI work, keep the established pipeline: UI UX Pro Max for direction, hue for the brand system artifacts, web-design-guidelines for web compliance, unslop for the final craft pass. Tokens and component rules are documented in `design-system/polaris-design/references/`.

## Conventions and gotchas

- TypeScript 7 has no `baseUrl`; `@shared` and `@renderer` are relative paths in `tsconfig.*.json` and `electron.vite.config.ts`. Keep them in sync.
- Existing style: 2 spaces, single quotes, no semicolons.
- Priorities are integers 0–3 (`0 无`, `1 低`, `2 中`, `3 高`). A recurrence rule requires a due date: the DB rejects a rule without one, and the UI disables the recurrence chips until a due date exists.
- better-sqlite3 is a native module rebuilt for Electron by electron-builder (`@electron/rebuild`, `asarUnpack: **/*.node`). Do not rebuild it for plain Node.
- Generated assets: `npm run make:icon` (`scripts/make-app-icon.mjs`) writes `build/icon.png`, `build/icon.ico` and `build/icon.icns` (the `build/Polaris.iconset/` intermediates are gitignored); `src/main/tray-icon.ts` is written by `make-app-icon.mjs` (`node scripts/make-tray-icon.mjs` is a thin wrapper forwarding to it); `node scripts/make-notice.mjs` regenerates `NOTICE` and `licenses/` from the installed production dependency closure — rerun it after dependency changes. Regenerate instead of hand-editing.
- `README.md` (Chinese) and `README.en.md` (English) are user-facing mirrors — update both in the same change when behavior, commands, or packaging change, keeping headings/tables/details structure in sync; each links to the other under the badges. Known limitations are listed there (mica reserved, reminders need the app running, un-complete recurrence semantics).
